## 一、基础认知与总体架构

### 1.1 什么是 AI Agent

AI Agent 是一种**以大语言模型(LLM)为核心控制器**的智能系统,具备:

- **自主性**:无需人类逐步指令,能独立决策和执行
- **目标驱动**:围绕特定目标持续运作,而非单次问答
- **状态记忆**:维护跨轮对话的上下文和长期知识
- **工具调用**:能调用外部 API、数据库、计算资源等扩展能力
- **反馈迭代**:根据环境反馈自我修正,形成闭环

**与传统 LLM 的区别**:

| 维度 | 传统 LLM | AI Agent |
|------|----------|----------|
| 交互模式 | 单次问答,无状态 | 多轮对话,有状态 |
| 知识来源 | 仅训练数据 | 训练数据 + 实时检索 + 工具调用 |
| 执行能力 | 生成文本 | 操作外部系统 |
| 自主性 | 被动响应 | 主动规划、自我修正 |

### 1.2 Agent 的四层结构

1. **目标层**:要完成什么任务、达到什么标准
2. **认知层**:推理、规划、反思、决策
3. **执行层**:工具调用、代码执行、外部系统交互
4. **治理层**:评估、安全、监控、成本与延迟控制

> 学 Agent 的核心,不是记名词,而是学会把这四层串成闭环。

### 1.3 三种常见 Agent 类型

| 类型 | 特点 | 适用场景 |
|------|------|----------|
| ReAct Agent | 思考-行动-观察循环,单步决策 | 实时交互、工具频繁调用 |
| Plan-and-Execute Agent | 先全局规划,再分步执行 | 长链路、多步骤任务 |
| AutoGPT Agent | 高度自主,自我驱动目标分解 | 开放式探索、研究任务 |

### 1.4 标准 Agent 架构

```text
用户交互层
    ↓
规划模块
    ↓
记忆 / 工具 / 反思
    ↓
执行与输出

（治理层为旁路：评估、安全、监控、成本控制贯穿以上各层）
```

### 1.5 框架速记

- **LangChain**:快速原型、多工具组合
- **LangGraph**:图结构工作流、持久化状态
- **Semantic Kernel**:企业级 SDK、微软生态
- **AutoGen / CrewAI**:多 Agent 协作
- **LlamaIndex**:检索与索引,重 RAG
- **Google ADK**:Agent 工作流与插件生态,适合上下文管理和多 Agent 编排
- **OpenClaw**:渠道 + Agent 平台,偏工程案例

### 1.6 LCEL 速记（低频，了解即可）

LCEL 用 `|` 把 LangChain 组件串成链（`prompt | llm | parser`，每个组件都是 `Runnable`，支持流式与异步）。2026 年面试几乎不考，知道是"链式编组 DSL"即可，时间优先给 MCP 与上下文工程。

### 1.7 高频题

- 什么是 AI Agent？与传统 LLM 有什么区别？
- Agent 的核心组件有哪些？它们如何协作？
- LangChain、LangGraph、LlamaIndex 分别适合什么场景？
- Agent 和 ChatBot 有什么区别？
- Agentic AI 的核心能力有哪些？

**简答**：

- **什么是 AI Agent**：本质是 `LLM + Planning + Memory + Tool Use + Feedback Loop`，和传统 LLM 的核心区别是它能围绕目标持续决策并调用外部能力完成任务。
- **核心组件如何协作**：先由认知层做规划和决策，再由执行层调用工具，记忆层提供状态与历史，治理层负责评估、安全、监控和成本控制。
- **框架如何选**：LangChain 适合快速原型，LangGraph 适合复杂状态机和工作流，LlamaIndex 更适合重检索和知识库场景。
- **Agent vs ChatBot**：ChatBot 偏向一问一答的闲聊；Agent 偏向任务达成，能在沙盒/系统中执行多步操作并改变环境状态。
- **Agentic AI 核心能力**：规划（Planning）、记忆（Memory）、工具使用（Tool Use）、行动与反思（Action & Reflection）。

### 1.8 Harness 与框架统一口径

本手册的"四层"与"推理 / 上下文 / 工具"三件套是同一系统的两种切分，对照如下：

| 四层 | 三件套 | 说明 |
|------|--------|------|
| 认知层 | 推理 | 规划、反思、决策都属于推理，由 LLM 实现 |
| （记忆层 + 部分执行层） | 上下文 | 本步决策能看到什么：先验 + 观察历史 + 动作历史 |
| （执行层接口部分） | 工具 | 允许读什么、做什么；执行本身在模型外 |
| 治理层 | 约束 + 验证 + 纠正 | 护栏，不在三件套内，单列 |

另记三句判断，资深面试用：

- **内化的是决策，不是执行**：RL 把"何时调、调哪个"写进参数，工具本身仍在外部跑。
- **模型定下限，系统定上限**：模型每内化一层，Harness 卸下一层，转而兜底新前沿。
- **Loop 只是程序实现**：循环代码（组装→调模型→执行→回填）层次低于"智能体与环境闭环交互"本身。

## 二、推理与决策机制

### 2.1 方法论演进：本质是测试时扩展

所有推理方法的本质都是**测试时扩展**：参数不动，让模型为答案花更多计算（更多 token / 更多时间）。两种花法：

- **并行采样**：同时生成多份推理再选优（Self-Consistency 多数投票、best-of-N、束搜索）。简单，但上限受制于模型一次能否走通。
- **串行修正**：基于上一步反思改错、迭代递进。必须配外部反馈（标准答案、单测、更强模型），裸自我修正可能把对的改错。

```text
直接回答 → CoT → ToT → GoT → Plan-and-Execute
```

| 方法 | 核心思想 | 场景 |
|------|----------|------|
| CoT | 线性推理，单链多占计算步 | 中等复杂任务 |
| ToT | 多路径探索 + 打分回溯 | 搜索、组合优化 |
| GoT | 图结构推理（了解即可，面试极少深问） | 多跳复杂依赖 |
| Plan-and-Execute | 先规划再执行，计划本身进上下文 | 长链路操作 |

补充:

- **Self-Consistency**:多条推理链投票,提高鲁棒性（并行采样的最简形态）
- **Reflexion / Self-Reflection**:失败后反思并修正（跨轮串行修正，不改参数）
- **思考模型**：o1/R1 这类模型把推理内化为原生能力（RL 训练，涌现反思回溯），对外暴露思考预算档位（reasoning effort）；简单题少想、难题多想，但过长思考可降质。选型看任务是否多步、预算是否可调。

### 2.2 ReAct

ReAct = **Reasoning + Acting**。

```text
Thought → Action → Observation → ...
```

- **Thought**:分析状态,判断是否要继续推理或调用工具
- **Action**:执行搜索、计算、API 调用等
- **Observation**:接收结果,回填下一轮 Thought

**ReAct vs Plan-and-Execute**:

- ReAct:单步决策、灵活、适合交互式任务
- Plan-and-Execute:先全局规划、适合步骤可预测任务

### 2.3 Self-Ask 与问题分解

把复杂问题拆成可检索、可验证的子问题,提升可解释性和鲁棒性。

### 2.4 ToT 轻量化实战

- 每步生成多个候选
- 用模型或规则打分
- 保留 Top-K 继续展开
- 不是所有场景都值得完整树搜索,很多时候束宽 `2~3` 即可

### 2.5 规划质量评估

- **完备性**:步骤是否覆盖完整
- **合理性**:顺序是否正确
- **可行性**:每步能否落地
- **效率**:步骤是否精简
- **容错性**:失败后是否可恢复

### 2.6 Self-Reflection 的工程用法

- **代码生成**:提交前检查类型错误、边界条件、测试缺口
- **故障排查**:围绕日志、现象、假设、验证结果闭环
- **最佳实践**:反思一次 + 验证一次,避免无限自言自语

### 2.7 高频题

- ReAct 框架的原理是什么？
- ReAct 和 Plan-and-Execute 有什么区别？
- CoT、ToT、GoT 分别适用什么场景？
- 什么是 Self-Reflection？
- 什么时候做多步规划，什么时候单步直出？
- 如何控制"过度规划"和"无效思考"？
- 如何处理长任务：分解、检查点、失败重试？
- **对比 CoT，ReAct 在模型与外部环境交互中解决了哪些痛点？**
- **实际开发中，如何判断用固定 Workflow 还是自主决策型 Agent？**

**简答**：

- **ReAct 原理**：通过 `Thought -> Action -> Observation` 循环，把推理和行动交替起来，让模型边想边做边根据反馈修正。
- **ReAct vs Plan-and-Execute**：前者灵活，适合交互式和工具频繁调用场景；后者先做全局规划，更适合长链路、步骤相对稳定的任务。
- **CoT / ToT / GoT**：CoT 适合线性推理，ToT 适合多路径搜索，GoT 适合复杂依赖和多跳问题。
- **Self-Reflection**：让模型针对已有结果做有限次自检和修正，但必须结合外部证据，否则容易空转。
- **多步 vs 单步**：单步直出适合任务边界清晰、链路短、工具组合简单的场景（如查天气）；多步规划适合长链路、需多源信息融合、极易中途跑偏的复杂任务（如写行业研报）。
- **控制过度规划**：设置硬性退出条件（Max Steps、Max Tokens、Timeout）；在 System Prompt 强调"一旦获得足够信息，立刻停止思考并输出结果"；引入监督者（Critic/Verifier）角色切断无效死循环。
- **长任务处理**：分解成 DAG 或子任务树；每完成一个重要节点写入外部状态（检查点 Checkpoint）；单步失败时把 Error Message 返回给 LLM 进行局部 Re-plan 或重试（限制重试次数）。
- **ReAct vs CoT 痛点解决**：CoT 只在模型内部做线性推理，无法获取外部实时信息，也不能验证推理正确性；ReAct 通过 Action 调用工具获取外部 Observation，解决了**知识时效性**、**事实可验证性**和**动态环境适应**三大痛点，形成"推理-行动-观察"的闭环。
- **Workflow vs Agent 选择**：任务边界清晰、步骤确定、成功标准明确、异常分支少的场景用固定 Workflow（如审批流）；任务边界模糊、需要动态决策、工具组合不确定、需要多轮探索的场景用自主 Agent（如研究分析）。核心判断标准是"确定性 vs 不确定性"。

## 三、记忆与上下文管理

### 3.1 记忆的三种类型

| 类型 | 内容 | 实现 |
|------|------|------|
| 短期记忆 | 对话上下文、当前步骤中间结果 | 上下文窗口、滑动窗口 |
| 长期记忆 | 用户偏好、历史决策、长期目标 | 向量库、知识图谱 |
| 外部记忆 | FAQ、文档、领域知识 | RAG、图数据库 |

> Memory 不是聊天记录堆叠,而是任务状态系统。

### 3.2 记忆管理的四个动作

- **写入**:何时记、记什么
- **读取**:如何取最相关记忆
- **更新**:冲突如何消解
- **遗忘**:如何淘汰低价值信息

### 3.3 多轮对话 Agent 设计

- **历史管理**:摘要 + 滑动窗口
- **记忆分层**:工作记忆 / 短期记忆 / 长期记忆
- **状态追踪**:维护 JSON 状态对象
- **上下文优化**:裁剪工具返回、分层存储、按需检索
- **调用编排**:跨轮参数传递、失败优雅降级
- **元控制**:不确定时澄清、话题切换时暂存恢复

### 3.4 工程实践要点

- 写入要有门槛,不是所有内容都值得持久化
- 分层检索:先短期,再长期,最后外部知识
- 冲突消解:时间优先或置信度优先
- PII 要脱敏或隔离存储

### 3.5 三层记忆架构

- 最内层:上下文窗口
- 中间层:Redis 会话缓存
- 最外层:向量库 + 关系库 + 图谱

检索优化:语义搜索 + 元数据过滤 + Reranker + 时间衰减。

#### 进阶补充:实体记忆与知识图谱

- 对时间、地点、人物、订单、任务等高价值实体,适合单独做结构化记忆,而不是只存文本摘要
- 常见做法是 `NER / 槽位抽取 -> 实体表或 JSON 状态 -> 按需回填上下文`
- 当问题涉及多实体关系、多跳推理、规则链依赖时,可引入知识图谱增强可解释性和可控性
- 图谱建设通常按 `本体定义 -> 抽取对齐 -> 图数据库存储 -> 查询服务 -> 增量更新` 五步走

### 3.6 长上下文压缩

- 系统指令、近期原文、远期摘要、按需检索四层保留
- 先删噪声,再做摘要
- 摘要要结构化,保留事实、决策、约束、未完成事项
- 摘要要可回溯,避免语义漂移
- **KV Cache 塑造拼法**：静态前缀（系统指令 + 工具 schema）放最前、长期不变以保缓存命中；轨迹只追加不改中间；动态注入（Skill 命中、检索片段）放末尾。压缩代价高是因为缓存全丢一轮，大返回落盘既省窗口也保缓存。

### 3.7 长期记忆淘汰

FIFO 的问题:

- 只看时间,不看价值
- 忽视访问频次和任务相关性
- 容易删掉高价值老记忆

优化:

- 时间衰减 + 使用频次 + 最近命中率 + 业务价值联合淘汰
- 先归纳成结构化画像,再删原始记录

### 3.8 高频题

- Agent 的记忆有哪些类型？如何管理？
- 长上下文记忆如何设计？如何避免信息过载？
- FIFO 记忆淘汰有什么问题？
- 什么时候需要把记忆做成知识图谱？
- 短期记忆 vs 长期记忆的边界是什么？
- 记忆写入策略：什么时候写、写什么、写到哪里？
- 记忆检索策略：向量检索 vs 关键词检索如何结合？
- 如何处理错误记忆与过期记忆？
- **长时对话场景下，如何实现上下文信息的动态压缩与选择性遗忘？**

**简答**：

- **记忆类型与管理**：通常分工作记忆、长期记忆和外部知识，管理上重点是写入门槛、分层检索、冲突消解和过期淘汰。
- **长上下文设计**：常用"近期原文 + 远期摘要 + 按需检索"的分层策略，并对工具返回和历史噪声做裁剪，避免窗口爆炸。
- **FIFO 问题**：它只看时间不看价值，容易删掉高价值老记忆，所以更合理的是时间衰减、使用频次和业务价值联合淘汰。
- **知识图谱何时需要**：当任务依赖实体关系、多跳查询、路径解释或复杂规则时，图谱比纯向量检索更稳定、更可解释。
- **短期 vs 长期记忆边界**：短期记忆是当前 Session 的多轮对话历史，随上下文窗口传递，Session 结束即清空；长期记忆是跨 Session 的信息（用户画像、偏好、历史核心事件），通常持久化在向量数据库或图数据库中。
- **记忆写入策略**：异步抽取，对话结束或每 N 轮后用小模型总结摘要与实体；写入介质：KV 存摘要，Vector DB 存细节片段，Graph DB 存关系。
- **记忆检索策略**：混合检索（Hybrid Search），向量捕捉语义相似度，关键词（BM25）保证特定名词/黑话的绝对召回。
- **错误与过期记忆处理**：为记忆打上时间戳（Timestamp）与衰减权重（Decay）；提供用户显式纠错的接口（CRUD 记忆池）。
- **动态压缩与选择性遗忘**：采用四层保留策略（系统指令 > 近期原文 > 远期摘要 > 按需检索）；先删除噪声（工具返回的冗余、重复确认），再做结构化摘要保留事实、决策、约束和未完成事项；遗忘策略采用"时间衰减 + 访问频次 + 业务价值"联合评分，而非简单 FIFO；对高价值实体（人名、订单、偏好）单独做结构化记忆，避免被压缩丢失。

## 四、工具调用与 MCP

### 4.1 工具调用六步流程

```text
任务识别 → 工具选择 → 参数生成 → 调用执行 → 结果校验 → 融合输出
```

### 4.2 Function Calling 的本质

- 本质是**受约束的结构化生成**
- LLM 负责决策和参数生成
- 外部 runtime 负责校验、执行、重试、超时、审计、回填

### 4.3 工具系统设计原则

- **参数契约**:明确输入输出 schema
- **权限边界**:最小权限原则
- **异常处理**:超时、重试、回退前置
- **可观测性**:输入、输出、耗时、错误可追踪
- **负面描述**:参数说明里要明确"不要怎么填",减少模型擅自猜参数
- **硬校验**:模型输出后仍要做类型、枚举、必填项校验
- **业务兜底**:关键参数如订单号、支付单号要二次校验,不能直接信任模型输出

### 4.4 安全六项框架

- **Schema 校验**
- **最小权限**
- **白名单**
- **执行隔离**
- **审计与熔断**
- **人工兜底**

### 4.5 常见失败与处理

| 错误类型 | 处理思路 |
|----------|----------|
| 参数错误 | schema 校验前置 |
| 选错工具 | 优化工具描述,引入路由层 |
| 执行超时 | 超时阈值、异步回调 |
| 权限不足 | 权限检查前置 |
| 返回值异常 | 格式校验 + 统一包装 |

### 4.6 失败时的用户反馈

- 明确区分超时、空值、权限不足、参数缺失
- 失败时禁止编造结果
- 模板:`发生了什么 -> 现在能做什么 -> 需要用户补充什么 -> 是否稍后重试`

### 4.7 调度引擎与终止判定

- 多工具依赖建议显式建 DAG
- LLM 负责"用哪个工具",编排层负责状态、重试、并发、幂等
- 终止条件看:目标是否满足、不确定性是否可消除、边际收益是否值得、风险是否允许

### 4.8 工具描述与弱 FC 模型优化

- 工具描述要强调"什么时候该用",不是只写"能做什么"
- 给固定 JSON 模板、枚举选项、few-shot 正反例
- 小模型可拆成 `tool routing -> argument filling` 两阶段
- 工具很多时可先做轻量路由,再只把 TopN schema 交给主模型
- 常见路由链路是 `关键词/小模型分类 -> 语义召回 -> 小模型重排 -> 主模型最终决策`

#### 进阶补充:工具过多时怎么路由

- 不要把上百个工具一次性全塞给模型,否则上下文浪费且误选率高
- 工程上常先做意图分类,再从工具库里召回候选工具,最后让主模型在候选集里决策
- 关键收益不是"更聪明",而是降低干扰、缩短上下文、提高工具命中率

### 4.9 MCP

MCP 是协议层,解决"怎么接":

- 标准化工具、资源、上下文的暴露方式
- 降低不同宿主与外部系统的对接成本
- 把能力声明与能力实现解耦
- 结构：`Host → 每服务一个 Client → Server`，JSON-RPC；`tools/list → tools/call` 取动作（模型自主选），`resources/list → read` 取数据（应用点选）
- 启动只载工具名与简介，用到才调详情（渐进式披露，省窗口也保 KV Cache）；大返回截断、分页、落盘

**MCP vs Skills**:

- MCP:协议层、互操作（接外部世界）
- Skills:能力封装层、经验复用（教何时如何用能力）。形态是文件夹 + SKILL.md，前 matter 写 name + description 作触发器，正文写步骤；三级加载：常驻索引约百 token → 命中读全文 → 按需读脚本引用（脚本只跑输出）
- 一句话：扩展加新能力，Skill 教用法，MCP 接外部，沙箱兜底

**A2A 补充**:

- A2A 更偏 Agent 与 Agent 之间的协作协议,适合跨平台、多厂商、多系统协同
- 它解决的是"代理之间怎么协商与传递任务",不是替代 Function Calling 或 MCP
- 面试里可一句话带过:MCP 偏工具接入,A2A 偏代理协作,实际落地远不如 MCP 常见

- 工具调用的完整流程是什么？
- MCP 解决了什么问题？和 Skills 有什么区别？
- Function Calling 的底层机制是什么？
- 多工具依赖时如何设计调度引擎？
- 工具很多时如何做路由？
- A2A 和 MCP 的区别是什么？
- 什么是工具调用（Tool Use）？什么时候不该用工具？
- 什么是函数调用（Function Calling）？和传统 RPC 的区别？
- 工具的接口设计原则是什么？
- 如何做工具调用的超时、重试、退避与熔断？
- 工具调用结果不可信时怎么做校验？
- 多工具串联：数据格式对齐与中间态设计？
- **详细阐述 Function Calling 完整流程，模型如何将自然语言语义转化为结构化参数？**

**简答**：

- **工具调用流程**：任务识别、工具选择、参数生成、执行调用、结果校验、融合输出六步闭环。
- **MCP 与 Skills**：MCP 解决"怎么标准化接工具和资源"，Skills 解决"如何把一套方法和经验封装成能力"。
- **Function Calling 本质**：不是模型真的执行函数，而是模型生成结构化调用意图，再由宿主程序负责校验、执行和结果回填。
- **多工具调度**：依赖关系复杂时要把流程显式建成 DAG 或状态机，让 LLM 决策，让编排层负责状态、重试、并发和幂等。
- **工具路由**：先缩候选集再让主模型选，常见是意图分类、语义召回、小模型重排三段式。
- **A2A vs MCP**：A2A 解决 Agent 之间的协作，MCP 解决模型与工具/资源的标准化接入。
- **Tool Use 定义与禁忌**：模型输出结构化指令由宿主环境解析执行；不该用的场景：可通过常识直接回答的问题、高危不可逆且缺乏人工确认的操作、对延迟极度敏感的简单规则场景。
- **Function Calling vs RPC**：Function Calling 是语义路由，参数由 LLM 模糊抽取与推理生成；传统 RPC 是强规则路由与确定性传参。
- **工具接口设计**：名称直白、描述清晰无歧义、参数越少越好；返回值遇到异常时返回明确错误提示；写操作必须考虑幂等性。
- **超时重试熔断**：代码层封装执行器设置 Timeout；失败时返回错误描述供 LLM 自我纠正，设置引擎层 `max_retries`；第三方接口持续失败时触发断路器（Circuit Breaker）。
- **结果校验**：编写专门的 Verifier 代码，或调用另一个 LLM 扮演 Critic 交叉验证；结果格式校验（Pydantic）。
- **多工具串联**：避免直接让 LLM 搬运大块数据，改用引用传递（如工具 A 返回 `file_id`，工具 B 接收 `file_id` 处理），减少 Token 消耗。
- **Function Calling 完整流程**：
  1. **工具声明**：宿主将工具 Schema（名称、描述、参数定义）注入 System Prompt
  2. **语义理解**：模型解析用户 Query，理解意图和所需参数
  3. **工具选择**：模型根据工具描述，判断是否需要调用及调用哪个工具
  4. **参数抽取**：模型从用户输入中抽取参数值，进行类型转换和格式对齐
  5. **结构化生成**：模型输出符合 JSON Schema 的调用指令（工具名 + 参数）
  6. **宿主校验**：外部 runtime 校验参数类型、必填项、枚举值、权限
  7. **执行与回填**：执行实际函数，将结果返回给模型继续推理
  
  语义到参数的转化依赖：工具描述的清晰度、Few-shot 示例、Schema 约束、模型的指令遵循能力。

## 五、知识系统与 RAG 工程

### 5.1 RAG 全链路

1. 文档解析与预处理
2. 分块(Chunking)
3. 向量化
4. 检索
5. 重排
6. 生成与引用

关键点:

- 文档解析要保留标题层级、页码、URL 等元数据
- 分块大小通常从 `200~500 tokens` 起步
- 检索常用向量 + BM25 双路召回
- 重排常用 Cross-Encoder
- 生成阶段要强引用、可拒答

### 5.2 线上治理

- 评测闭环
- 成本监控
- 增量同步、去重、版本管理
- 降级策略:检索失败 fallback、只返回引用内容

### 5.3 RAG 评估指标

- 上下文相关性
- 答案忠实性
- 答案相关性
- 召回率
- 引用覆盖率

### 5.4 幻觉治理

- **输入层**:提高检索质量,明确知识边界
- **生成层**:低温度、强引用、置信度输出
- **校验层**:事实、一致性、逻辑校验
- **线上层**:用户反馈、幻觉检测、指标复盘
- **兜底层**:高风险场景人工审核

### 5.5 长文档分块

- 优先按结构切,再用窗口兜底
- FAQ 适合按问答对切
- 表格按表头 + 行块切
- 代码按函数 / 类切
- 父子分块适合长文档

### 5.6 Rerank 与 TopK

- 向量检索快,但打分粗
- Cross-Encoder 慢,但精度高
- 常见做法:先召回 `20~50`,重排后截断 `3~5`
- 离线看 MRR、NDCG@K、Recall@K
- 在线看忠实性、首答命中率、用户追问率

### 5.7 静态知识库、动态网页与时效性

- 静态知识库:稳定、可审计、可控
- 动态网页:适合强时效,但噪声更高
- 不能只看语义相关,还要考虑新鲜度
- 事实类信息要加时间权重和二次验证

#### 结构化数据 vs 非结构化数据

- 结构化数据优先走 `SQL / Text-to-SQL / Pandas Agent` 这类确定性查询链路
- 非结构化数据优先走 `RAG`,通过分块、检索、重排、引用约束来生成答案
- 不要把所有问题都塞进 RAG,表格、数据库、报表类问题通常更适合结构化查询

### 5.8 Agentic RAG vs 传统 RAG

- 传统 RAG:固定流水线
- Agentic RAG:会动态决定是否检索、如何改写 query、是否追问用户
- 优势是灵活,代价是时延、成本、安全治理都更复杂

#### 进阶补充:知识图谱与图增强检索

- 纯向量检索擅长找相似文本,但对多跳关系和路径解释不稳定
- 当问题依赖实体关系、层级依赖、规则链时,可把图谱作为 RAG 的补充而不是替代
- 常见模式是 `文本检索拿证据 + 图查询拿关系路径 + LLM 负责整合解释`

### 5.9 高频题

- 设计一个线上可用的 RAG 系统，你怎么做？
- 幻觉如何治理？
- 长文档切片、Rerank、TopK 怎么定？
- 什么时候用静态知识库，什么时候用动态网页？
- 什么时候该上知识图谱或图增强检索？
- RAG 的完整链路是什么？
- Chunking 如何做？按段/按句/滑窗怎么选？
- Embedding 模型如何选择与评估？
- 召回与排序：TopK、重排（rerank）怎么做？
- 如何降低幻觉：引用、可追溯、拒答策略？
- 如何做增量更新与一致性（文档变更、索引刷新）？
- **RAG 检索获取的外部知识，如何精准输入给模型并避免无关知识干扰？**
- **重排序（Rerank）技术的定义，在检索链路中对决策准确性的关键作用？**

**简答**：

- **RAG 系统设计**：按 `解析 -> 分块 -> 向量化 -> 检索 -> 重排 -> 生成引用` 六段讲，并强调可评测、可回滚、可降级。
- **幻觉治理**：从输入质量、生成约束、事实校验、线上监控和人工兜底五层一起做，不能指望单点解决。
- **分块 / Rerank / TopK**：先按结构切块，召回阶段宁可宽一点，重排后再截到 `Top3~5`，最终靠离线排序指标和线上答案质量联合调参。
- **静态库 vs 动态网页**：稳定、可审计问题优先静态知识库；强时效问题补动态检索，但要加白名单、引用和时间校验。
- **知识图谱何时上**：当问题依赖实体关系、多跳路径、可解释查询时，引入图谱比只堆向量召回更稳。
- **RAG 完整链路**：文档解析提取 → Chunking（分块） → Embedding/倒排索引建库 → 用户 Query 处理/改写 → 召回（Retriever） → 排序过滤（Rerank） → 拼接 Prompt 生成。
- **Chunking 策略**：按段落（自然语义）为主，补充固定长度+滑窗重叠（Overlap）防止截断关键信息；高阶可用语义分块（Semantic Chunking）或知识图谱（GraphRAG）。
- **Embedding 选择**：结合业务语言（中英/多语言）与领域微调；使用 MTEB 榜单参考，结合自有金标准（Query-Doc 对）评估召回率。
- **召回与重排**：双路召回 Dense（向量） + Sparse（BM25）；用 Cross-Encoder 模型对召回结果进行打分精排，剔除无关片段。
- **降低幻觉**：强行要求大模型在生成时标注来源（如 `[doc1]`）；兜底 Prompt："如果参考资料中没有答案，请回答不知道"。
- **增量更新**：为每个文档维护 Hash 或版本号，变更时执行先删后插（Upsert）。
- **精准输入与避免干扰**：
  - **检索阶段**：通过混合检索（向量+关键词）提高召回相关性，设置相关性阈值过滤低分片段
  - **重排阶段**：用 Cross-Encoder 精排，剔除语义相关但内容无关的"伪相关"片段
  - **输入控制**：限制注入模型的上下文长度（通常 Top3~5），避免信息过载
  - **Prompt 工程**：明确告知模型"仅基于以下参考资料回答"，并强制要求引用标注
  - **拒答机制**：当检索结果相关性均低于阈值时，触发"知识不足"兜底，而非强行生成
- **Rerank 定义与关键作用**：
  - **定义**：在粗排召回（如向量检索）之后，用更精确的模型（通常是 Cross-Encoder）对候选文档重新打分排序
  - **关键作用**：
    1. **精度提升**：Cross-Encoder 能捕捉 Query 和 Doc 的细粒度交互，比双塔向量模型更准
    2. **伪相关过滤**：剔除"语义相近但内容不相关"的噪声片段
    3. **结果截断依据**：重排分数为最终取 TopK 提供可靠依据
    4. **质量兜底**：离线可用 MRR、NDCG 评估，在线可看首答命中率和用户追问率

## 六、多 Agent 与复杂编排

### 6.1 单 Agent vs 多 Agent

**单 Agent 适用**:

- 任务边界清晰
- 延迟要求严格
- 团队资源有限

**多 Agent 适用**:

- 任务复杂,单 Agent 稳定性不足
- 需要规划、执行、审查分工
- 需要错误隔离

### 6.2 常见协作模式

- **点对点**
- **黑板模式**
- **监督者模式**
- **流水线模式**

### 6.3 通信协议

- Manager-Worker
- 消息队列
- 共享 Memory

### 6.4 起步配置

- `Planner + Executor`
- 再加 `Reviewer`
- 需要路由时再加 `Router`

### 6.5 风险控制

- 明确输入输出契约
- 设置中间验收点
- 限制可共享信息边界

### 6.6 冲突与收敛

- 先定权责边界
- 把争议对象结构化
- 引入裁决机制
- 限制轮次和成本

### 6.7 高频题

- 什么时候需要多 Agent？
- 多 Agent 如何协作？常见通信模式有哪些？
- 如何解决冲突、分歧和不收敛？
- 多 Agent 的分工方式有哪些？（Planner/Executor/Verifier）
- 多 Agent 如何共享上下文与状态？如何避免串扰？
- 多 Agent 协商冲突怎么处理？最终决策如何落地？
- 多 Agent 的成本与收益如何评估？
- **单 Agent 处理复杂长周期任务时，引入 Multi Agent 的核心优势？**
- **Multi Agent 系统中 Router 节点依据哪些规则分发任务？**
- **什么是 Human-in-the-loop？如何设计人工审批断点保障可靠性？**

**简答**：

- **什么时候上多 Agent**：当任务过长、角色天然分工明显、单 Agent 稳定性下降或需要错误隔离时再上，不要为"高级感"而拆。
- **如何协作**：常见有点对点、黑板模式、监督者模式、流水线模式；通信实现上常用 Manager-Worker、消息队列和共享 Memory。
- **如何处理冲突**：先定权责，再把争议对象结构化，最后通过 Supervisor、规则优先级、投票或人工裁决实现收敛。
- **分工方式**：垂直分工（按业务领域分：代码 Agent、测试 Agent、文档 Agent）；流程分工（按角色分：Manager 派发任务，Worker 执行，Critic 验收）。
- **共享上下文与避免串扰**：引入全局共享的"白板（Scratchpad）"或状态图；限制 Agent 间的可见域，只传递必要的消息（Message/Artifact）。
- **冲突处理与决策落地**：引入 Supervisor 节点进行裁决；或者使用多数投票机制（Majority Voting）。
- **成本与收益评估**：关注边际效用，多加一个 Critic 提升的正确率是否能弥补增加的 Token 消耗和延迟。
- **Multi Agent 核心优势**：
  1. **认知卸载**：将复杂任务拆解到不同专业 Agent，降低单个 Agent 的认知负担
  2. **错误隔离**：单个 Agent 失败不会导致整体崩溃，局部可重试或降级
  3. **专业分工**：不同 Agent 专注不同领域（如代码、测试、文档），输出质量更高
  4. **并行效率**：无依赖的子任务可并行执行，缩短总耗时
  5. **可解释性**：每个 Agent 的输入输出清晰，便于调试和审计
- **Router 分发规则**：
  1. **意图分类**：基于用户 Query 的意图识别（如"写代码"→Coder，"查数据"→Analyst）
  2. **实体匹配**：根据抽取的实体类型路由（如"订单问题"→订单 Agent）
  3. **历史状态**：结合当前会话状态和历史分工，保持连续性
  4. **负载均衡**：考虑各 Agent 的当前负载和响应能力
  5. **规则兜底**：明确默认路由和异常回退路径，避免 Router 本身成为单点故障
- **Human-in-the-loop 设计**：
  - **定义**：在 Agent 自主执行的关键节点引入人工审批或确认机制，形成"AI 执行 + 人类监督"的混合模式
  - **断点设计原则**：
    1. **风险分级**：高危操作（支付、删除、发布）必须人工确认；低风险操作（查询、预览）可自动执行
    2. **时机选择**：在"计划确认"（是否按此方案执行）和"结果验收"（是否接受此结果）两个关键节点设置断点
    3. **信息完整**：提交人工审批时，必须附带完整上下文（计划内容、影响范围、回滚方案）
    4. **超时机制**：人工审批设置超时时间，超时后自动回退或降级
    5. **批量模式**：对信任度高的用户/场景，支持"记住选择"减少重复审批
  - **可靠性保障**：人工断点本身要有熔断机制，当审批系统故障时，默认拒绝或转人工客服，不能阻塞在待审批状态。

## 七、评估、安全与治理

### 7.1 评估指标分层

| 层级 | 指标 |
|------|------|
| 任务层 | 完成率、拒答率、回退率 |
| 推理层 | 步骤正确率、自检通过率 |
| 工具层 | 调用成功率、重试次数 |
| 运营层 | P95 时延、成本、稳定性 |

### 7.2 误差分析框架

1. 采样失败用例
2. 按意图错、检索错、推理错、执行错分桶
3. 用 `影响 × 频率 × 修复成本` 排优先级
4. 做最小修复并回归评估

### 7.3 迭代节奏

- 每周离线评估
- 每两周更新 Prompt / 工具 / 流程
- 每月复盘质量、成本、时延

### 7.4 安全风险

- 提示注入
- 越权调用
- 数据泄漏
- 输出合规
- 无限循环

### 7.5 安全设计原则

- 纵深防御
- 早期失败
- 明确错误信息
- 人工兜底
- 高风险写操作先 `dry-run`,给操作预览,再决定是否真正执行
- 删除、支付、批量修改等动作要支持审批链、回滚点和审计回放

### 7.6 Claude Code 四层权限模型

1. 企业级策略
2. 项目级规则
3. 用户级偏好
4. 工具级默认策略

启发:

- 安全不是补丁,而是第一设计
- 只读、写入、高危操作要分层处理

细节补充:

- 当前三层还无法决策时,可以引入轻量分类器先快筛,再交给更强模型做二次判断
- 模式层本质是不同风险偏好的执行模式,如默认确认、接受编辑、全放行、严格拒绝
- 高危工具不能只靠 Prompt 约束,而要在 runtime 做硬编码拦截

### 7.7 经验沉淀

- 把成功路径、失败原因、人工修正结构化存储
- 经验要可检索
- 反思要落成规则
- 新经验要灰度验证

### 7.8 高频题

- 如何评估 Agent 性能？
- Agent 系统如何做安全机制？
- Claude Code 的权限模型有什么启发？
- 如何让 Agent 具备自我学习能力？
- 反思（self-reflection）什么时候有效，什么时候无效？
- 如何做答案验证：基于规则、基于测试、基于工具？
- 如何做事实性校验与引用管理？
- 如何处理不确定性：如何"可控地猜测"？
- 提示词注入、数据外泄、越权工具调用如何防护？
- 如何做权限与审计：谁调用了什么工具、访问了什么数据？
- 如何做内容安全：敏感信息、合规、风控？
- **有哪些量化评估方式可以衡量 Agent 系统优劣？**
- **除模型生成质量外，还需关注哪些维度的评估指标？**
- **针对多步推理的响应延迟问题，可落地的优化方法？**
- **上下文窗口持续扩容，传统 RAG 是否会被完全替代？**

**简答**：

- **如何评估性能**：至少分任务层、推理层、工具层、运营层四层指标，再配错误分桶和回归评测。
- **安全机制怎么做**：输入过滤、工具权限、执行隔离、输出审计、熔断降级和人工审批要一起上。
- **Claude Code 的启发**：安全必须分层治理，且高危操作要硬拦截，不能只靠提示词约束。
- **自我学习能力**：关键不是"自动变聪明"，而是把成功路径、失败案例和人工修正沉淀成可检索、可验证、可灰度的系统经验。
- **反思有效性**：有效场景：代码编写、数学推导等有客观对错标准的任务（结合编译器反馈）；无效场景：纯常识或价值观问题，容易被绕晕或自我推翻。
- **答案验证**：代码/SQL 用执行结果验证；格式用正则/Schema 验证；逻辑用大模型打分验证。
- **事实性校验**：后置一个轻量级 NLI（自然语言推理）模型检查生成文本是否蕴含于检索片段中。
- **不确定性处理**：允许模型输出 Confidence Score，低于阈值触发人类介入（Human-in-the-loop）。
- **安全防护**：将危险工具（发邮件、转账）设置为"需人工审批（Human Approval）"。
- **权限与审计**：拦截层校验 Session Token 对应的用户权限；操作落库留痕。
- **内容安全**：接入专门的内容安全网关（如文本审校 API），屏蔽涉政/黄暴词汇。
- **量化评估方式**：
  1. **任务完成率**：成功完成任务的比率（最核心）
  2. **步骤正确率**：每步推理和工具调用的正确性
  3. **用户满意度**：人工评分或 NPS
  4. **回归评测**：固定评测集上各版本的指标对比
  5. **A/B 测试**：线上分流对比不同策略的效果
  6. **错误分桶分析**：按错误类型分类统计，定位薄弱环节
- **其他关键评估维度**：
  - **成本维度**：Token 消耗、工具调用次数、API 费用
  - **延迟维度**：首字延迟、端到端延迟、每步平均耗时
  - **稳定性维度**：服务可用性、错误率、重试成功率
  - **安全维度**：越权调用率、敏感信息泄露率、提示注入拦截率
  - **可解释性维度**：决策可追溯比例、引用覆盖率
- **延迟优化方法**：
  1. **模型分级**：简单任务用小模型，复杂任务才用大模型
  2. **流式输出**：先返回"思考中"状态，逐步输出结果，降低感知延迟
  3. **并行调用**：无依赖的工具调用并行执行
  4. **缓存复用**：Semantic Cache 命中历史相似查询，直接返回答案
  5. **异步化**：非实时任务（如报告生成）走异步队列
  6. **步数限制**：设置 Max Steps 和 Max Tokens 上限，防止无限循环
  7. **Prompt 压缩**：精简工具描述和历史上下文，减少传输和计算量
- **RAG 是否会被长上下文替代**：
  - **核心观点**：不会完全替代，而是互补共存
  - **理由**：
    1. **成本问题**：长上下文虽然能装下更多内容，但 Token 成本随长度线性甚至超线性增长，全量加载不经济
    2. **噪声问题**：上下文过长会导致"迷失在中间"，无关信息干扰模型判断，RAG 的检索筛选能精准定位相关内容
    3. **时效性问题**：RAG 能接入实时更新的外部知识，而长上下文只能依赖训练数据或单次注入
    4. **可解释性**：RAG 的引用溯源比"模型从长上下文中记住"更可审计
    5. **结构化查询**：RAG 可结合关键词、元数据过滤、图谱查询等结构化手段，纯长上下文缺乏这种灵活性
  - **趋势**：长上下文会改变 RAG 的形态（如更大的 Chunk、更粗的召回），但检索-筛选-引用的核心逻辑仍不可替代。

## 八、工程案例与落地实践

### 8.1 OpenClaw / Claude Code / Hermes Agent 架构对比

> 这里的 `Hermes Agent` 按"通用执行型 Agent / Browser-Use 型 Agent"抽象,用于和 `OpenClaw`、`Claude Code` 做工程视角对比。
>
> **注意：`Hermes Agent` 是为讲清分类虚构的对照物，并非真实开源项目，面试时不要当真实案例引用。** 要举真实执行型案例可用 SWE-agent / OpenHands / Karpathy autoresearch。

| 维度 | OpenClaw | Claude Code | Hermes Agent |
|------|----------|-------------|--------------|
| 定位 | 平台底座,重渠道与插件扩展 | 工程助手,重代码闭环 | 执行型 Agent,重环境交互 |
| 结构 | Manifest + Adapter + 统一消息模型 | 交互层 + Agent 核心 + 工具 + 安全 + 记忆 | Planner + Executor + Observer + Action |
| 规划 | 平台编排,可插拔规划 | ReAct 主循环 + 子任务拆分 | 任务分解 + 观察反馈闭环 |
| 记忆 | 能力声明 + 运行态状态分层 | `CLAUDE.md` + PromptCache + 上下文压缩 | 会话状态 + 轨迹 + 环境快照 |
| 工具 | Manifest 暴露插件和渠道能力 | 内建工具丰富,支持延迟加载 | 浏览器动作、页面理解、表单执行 |
| 安全 | 插件边界、渠道隔离、导入导出约束 | 权限分层 + 高危操作硬拦截 | 动作白名单 + 环境隔离 + 回放审计 |
| 优势 | 生态扩展强,适合多渠道平台化 | 工程任务强,闭环和自愈能力好 | 页面驱动任务强,感知-动作链路直接 |
| 局限 | 平台强于业务智能,业务编排要另补 | 体系复杂,上下文与安全治理成本高 | 易受 UI 变化影响,动作稳定性要求高 |

**一句话对比**:

- **OpenClaw** 更像"Agent 平台底座"
- **Claude Code** 更像"工程助手型 Agent"
- **Hermes Agent** 更像"执行型 / 环境交互型 Agent"

**细节补充**:

- **OpenClaw**:核心思想是 `manifest-first + adapter + common schema`,先声明能力,再按需加载实现
- **Claude Code**:除了主 Agent,还会有 `Teammate / Fork / Background / Remote` 这类子 Agent 形态,适合大型工程协作
- **Claude Code**:`PromptCache`、上下文压缩、后台监听测试/构建日志,本质都是"上下文工程 + 反馈闭环"

### 8.2 客户支持 Agent 系统案例

链路:

```text
用户渠道 -> 网关层 -> Q&A Agent -> Router Agent -> 各业务子代理
```

关键取舍:

- 简单固定流程用工作流
- 复杂多步骤用 Agent
- 中央大脑先即时响应,后台异步执行
- 超能力范围时转人工

工程补充:

- 网关层通常还要补齐认证、PII 脱敏、限流、重复检测和请求计数
- Planner 在真正调用退款、物流、订单工具前,最好先走策略检查和政策一致性校验
- 数据层一般不是单库,而是关系库存交易状态、向量库存政策与 FAQ

### 8.3 架构启示

- **OpenClaw** 的启发:当渠道和插件数量上来后,声明式注册优于硬编码依赖。
- **Claude Code** 的启发:安全、记忆、工具和上下文工程必须一体化设计,不能后补。
- **Hermes Agent** 的启发:环境交互型 Agent 的核心不只是推理,而是"感知 -> 动作 -> 验证"的稳定闭环。

#### 进阶补充:Manifest 与 Runtime 状态

- `Manifest` 更适合声明静态能力、权限、配置 schema,不适合承载"是否已认证"这类动态状态
- 动态状态应留在运行时层,如认证状态、连接状态、速率限制状态、缓存状态
- 工程上要把"能力声明"和"运行时状态"拆开,否则插件发现、验证和热加载都会变复杂

### 8.4 自建 Agent 的生产级落地表

| 阶段 | 目标 | 核心产物 | 注意点 |
|------|------|----------|--------|
| 闭环定义 | 定边界 | 输入输出、成功标准、失败回退 | 先定闭环,不先写 Prompt |
| 最小闭环 | 跑通单场景 | 单 Agent Demo、工具调用、基础记忆 | 先单 Agent,再决定是否拆多 Agent |
| 架构分层 | 建骨架 | 模型、工具、记忆/RAG、编排、治理 | 路由、权限、重试不要全塞给 LLM |
| 评测治理 | 可量化迭代 | 评测集、错误分桶、回归脚本 | 没评测就无法稳定优化 |
| 线上控制 | 可上线 | 埋点、灰度、熔断、审批链 | 关键是可观测、可回滚、可审计 |
| 成本时延 | 可持续 | 缓存、模型分级、步数上限、异步化 | 优先减少轮次和上下文长度 |

补充:

- **DevSpec / 设计文档先行**:把系统概述、技术选型、目录结构、测试方案、阶段排期先写清楚,再让 Agent 参与实现
- **Workflow Skills**:可把同步文档、实现、测试、阶段检查做成可复用能力,降低长项目漂移
- **Sandbox Runtime**:代码执行型 Agent 最好运行在 Docker / Wasm / E2B 这类沙箱里,并支持 pause、resume、snapshot

### 8.5 最小可用实现路径

- Week 1:任务流图 + 成功标准
- Week 2:最小 Agent Demo
- Week 3:评估脚本 + 错误分桶
- Week 4:多 Agent 或图谱增强检索原型

### 8.6 成本与延迟控制

- 设置步数、调用次数、Token 上限
- 做缓存
- 模型分级
- 非实时任务异步化
- 优先减少轮次和上下文长度

### 8.7 模型选型

- 按任务拆模型
- 同时看效果、时延、成本、稳定性、合规性
- 常见做法是多模型路由

### 8.8 流式输出

- 先确认任务理解
- 再显示检索、调用、汇总等状态
- 事件流化:`planning` / `tool_start` / `tool_result` / `retry` / `final_answer`

### 8.10 高频题

- 如何自建一个 Agent 系统，并把它做到生产级落地？
- 如何控制 Agent 的成本和延迟？
- 描述一个你设计或实现过的 Agent 系统。
- 如何设计 Agent 的流式输出？
- 代码执行型 Agent 怎么做安全隔离？
- Agent 的状态机/工作流如何建模？
- 如何做会话隔离与多租户？
- 如何做缓存：prompt cache、tool result cache、embedding cache？
- 如何做容错：降级为纯检索/纯规则/人工兜底？
- 如何控制成本：token、工具调用次数、并发与队列？

**简答**：

- **生产级落地**：先定闭环，再做单 Agent 最小闭环，随后补齐分层架构、评测治理、灰度发布、熔断降级和审批链。
- **成本与延迟控制**：核心是限制轮次、控制上下文、做缓存、模型分级和异步化，而不是一味换更便宜的模型。
- **项目题怎么答**：按"目标 -> 架构 -> 关键取舍 -> 治理机制 -> 结果指标"讲，突出可交付和可回归。
- **流式输出怎么做**：把任务理解、检索状态、工具执行、阶段结果和最终答案拆成事件流，避免用户空等。
- **安全隔离怎么做**：高风险执行放进沙箱 runtime，限制文件、进程、网络和资源配额，并保留审计、快照和回滚能力。
- **状态机建模**：推荐使用图计算框架（如 LangGraph），将状态视为节点，操作视为边。
- **会话隔离与多租户**：Session ID 与 User ID 强绑定，缓存与数据库严格做租户物理/逻辑隔离。
- **缓存策略**：Semantic Cache 通过向量检索命中历史相似问答，直接返回答案；Tool Result Cache 对相同参数的工具调用复用结果；KV Cache 是推理加速层的注意力键值复用（见 9.3）。三者不在同一层，不要混用。
- **容错降级**：当大模型服务熔断时，返回兜底话术或切给人工客服。
- **成本控制**：限制最大步数（Max Iterations）；使用小模型做路由，大模型做推理；截断冗长工具返回。

## 九、LLM 底层机制与性能优化

### 9.1 Prompt 处理流程

Prompt 进入 LLM 后会经历:

1. 分词(Tokenization)
2. 嵌入(Embedding)
3. Transformer 计算
4. 解码生成

### 9.2 微调与强化学习

- **SFT**:提升指令遵循
- **LoRA / QLoRA**:低成本领域适配
- **RLHF / DPO / PPO / GRPO**:偏好对齐与策略优化

### 9.3 推理加速

- 量化
- 蒸馏
- KV Cache
- Flash Attention
- Paged Attention(vLLM)

框架速记:

- `vLLM`:吞吐优先
- `TensorRT-LLM`:低延迟
- `TGI`:开箱即用
- `Ollama`:本地开发测试

### 9.4 RL Agent vs Prompt Agent

- Prompt Agent:上线快、调试成本低
- RL Agent:更像真正的序列决策,但训练与安全成本更高
- 现实里常见混合方案:先 Prompt/Workflow,后局部 RL 优化

### 9.5 高频题

- Prompt 进入 LLM 后经历了什么？
- LoRA 微调的原理是什么？
- 推理加速有哪些手段？
- RL Agent 与 Prompt Agent 的区别是什么？
- 什么是上下文窗口？对 Agent 设计有什么影响？
- System / Developer / User 指令优先级如何处理？
- 结构化输出（JSON Schema）如何保证稳定？
- 如何做 Prompt 模板化与版本治理？
- 如何降低提示词注入（Prompt Injection）风险？

**简答**：

- **Prompt 处理流程**：分词、嵌入、Transformer 计算、解码生成四步。
- **LoRA 原理**：冻结原模型大部分参数，只训练低秩增量矩阵，用很小的训练成本完成领域适配。
- **推理加速**：常见手段有量化、蒸馏、KV Cache、Flash Attention、Paged Attention。
- **RL Agent vs Prompt Agent**：前者学策略，适合长期决策；后者依赖上下文内推理和工作流设计，上线更快、工程成本更低。
- **上下文窗口影响**：窗口小会导致"失忆"或无法放入足够的工具描述与召回内容；窗口大会增加成本、延迟，并可能导致"迷失在中间（Lost in the middle）"。因此需要精简 Prompt、分页、记忆摘要等手段。
- **指令优先级**：现代 LLM 通常赋予 System/Developer prompt 最高的遵循优先级，用于设定人设、底线规则；User prompt 用于承载当次具体任务。若两者冲突，安全对齐好的模型应坚守 System 规则。
- **结构化输出稳定**：明确定义 Schema（Type, Enum, Required）；提供 Few-shot 示例（正例与边界负例）；开启大模型原生的 `response_format: { "type": "json_object" }` 或 Structured Outputs 模式；增加解析失败时的重试机制（把错误栈喂给 LLM 修复）。
- **Prompt 版本治理**：将 Prompt 与代码解耦，存入配置中心、数据库或专用的 Prompt CMS（如 LangSmith）；使用 Jinja2/Jinja-like 模板引擎占位变量；实行版本控制（Git/语义化版本），结合 A/B 测试评估新旧版本效果。
- **提示词注入防护**：使用明确的定界符（如 `<user_input>...</user_input>`）包裹不可信数据；用轻量级分类器或独立 LLM 预先过滤危险输入；工具执行前加入人为确认或黑名单拦截。

### 10.2 高频题答题框架

- **RAG 系统设计**:解析 -> 分块 -> 向量化 -> 双路召回 -> 重排 -> 生成引用,强调"可控、可评测、可降级"
- **幻觉治理**:输入层 -> 生成层 -> 校验层 -> 线上层 -> 人工兜底
- **工具安全**:Schema -> 权限 -> 白名单 -> 隔离 -> 审计熔断 -> 人工兜底
- **你做过 Agent 吗**:目标、认知、执行、治理四层闭环
- **质量如何保证**:指标 + 分桶 + 回归
- **为什么多 Agent**:降认知负担 + 中间验收点
- **如何控成本**:上限、缓存、回退、模型分级

### 10.3 大厂真题方向

- **京东:电商客服 Agent**
- 常见追问 1:多轮对话状态管理如何设计?
- 答:把状态拆成 `用户意图 + 当前订单/商品实体 + 槽位参数 + 当前阶段 + 是否转人工` 五部分;短期状态放会话缓存,关键业务状态回写数据库;上下文用"近期原文 + 结构化摘要"混合保留,避免窗口爆炸。
- 常见追问 2:订单相关查询如何路由到不同子 Agent?
- 答:先做意图识别,再结合实体抽取和权限校验进行路由;退款、换货、物流分别走独立 Specialist;路由层负责兜底和回退,不能把所有分发逻辑都交给 LLM。
- 常见追问 3:什么时候必须转人工?
- 答:用户情绪激烈、金额争议、策略边界外请求、模型低置信度、多次重试失败时立即转人工,并把当前摘要和证据链一并交接。

- **字节:审核 / 内容安全 Agent**
- 常见追问 1:高并发下如何保证稳定性?
- 答:入口层做限流、队列削峰和超时熔断;模型服务做多级降级,大模型只处理高不确定样本;简单样本优先走规则和轻模型,减少高峰期推理压力。
- 常见追问 2:审核结果不一致时怎么办?
- 答:先区分规则冲突、模型波动和多模态信息不全;高风险内容引入复核链路,输出"标签 + 证据 + 置信度";最终用规则优先级或人工裁决保证收敛。
- 常见追问 3:如何降低误杀和漏放?
- 答:离线按错误类型分桶,分别优化召回和精度;线上保留申诉反馈闭环,把人工改判样本回灌评测集和训练集。

- **小红书:推荐 / 社区内容 Agent**
- 常见追问 1:个性化和多样性如何平衡?
- 答:先用兴趣相关性保证命中,再在重排阶段加入类目去重、新颖度和探索权重;工程上通常做多目标排序,而不是只追点击率。
- 常见追问 2:用户偏好如何从短期记忆沉淀到长期记忆?
- 答:把短期行为信号按频次、持续时间、任务相关性做聚合,达到阈值后再写入长期画像;不要把单次偶发行为直接写成稳定偏好。
- 常见追问 3:如何避免推荐越推越窄?
- 答:在召回和重排都保留探索流量,加入新主题注入和相似内容去重;长期画像要有时间衰减,避免旧兴趣长期绑死用户。

- **阿里:多 Agent 订单处理系统**
- 常见追问 1:多 Agent 间的事务一致性如何保证?
- 答:关键写操作不能只靠自然语言协作,必须落到工作流或状态机;订单、库存、支付等核心链路要有幂等键、状态表和补偿机制。
- 常见追问 2:支付回调乱序、重复、丢失怎么处理?
- 答:乱序靠状态机只允许合法跃迁;重复靠幂等键去重;丢失靠补偿任务和对账任务兜底,不能把一致性寄希望于单次回调成功。
- 常见追问 3:为什么这里不适合纯 ReAct?
- 答:因为订单处理是强约束、高风险场景,确定性流程和状态机比自由推理更重要;LLM 更适合做异常解释、辅助决策和用户沟通。

- **安克:多语言 Agent / 跨境场景**
- 常见追问 1:多语言场景下如何保证 RAG 检索质量?
- 答:优先做语言识别和查询标准化;索引层可选多语向量模型或"翻译到枢轴语言 + 检索"的双路方案;评测时按语言分桶,不能只看总指标。
- 常见追问 2:不同地区合规要求怎么处理?
- 答:把地区、品类、监管规则做成显式策略层,不要只写在 Prompt 里;回答前结合用户地区、商品类型、风险等级匹配对应规则模板。
- 常见追问 3:如何处理翻译造成的语义偏差?
- 答:高风险字段如金额、时效、法规条款尽量保留原文引用;生成层输出"本地语言答案 + 原文依据",必要时回源校验,避免二次翻译失真。

**统一答题思路**:

- 先讲业务目标和约束:高并发、强一致、低时延、合规、转人工要求
- 再讲系统拆层:路由层、状态层、工具层、治理层
- 最后讲兜底机制:评测、熔断、人工复核、审计回放
